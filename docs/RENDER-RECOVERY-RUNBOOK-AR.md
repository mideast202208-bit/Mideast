# تشغيل واستعادة Middle East على Render — إصدار مراجعة 0.10

هذه الحزمة معدّة للمراجعة. لا تطبقها على الإنتاج قبل: نسخة متسقة من الإنتاج، تحقق مسارات القرص، تأمين مفتاح الاستعادة، تفويض Google Drive، وموافقة المالك على فترة النشر القصيرة وإعدادات الإنتاج. لا تنقل PostgreSQL ولا تغيّر Wuilt أو Odoo.

## البيانات والتخزين

القاعدة SQLite باستخدام `node:sqlite`. المسار الافتراضي في Docker `/app/data/mid-east.sqlite`، ومفتاح AES الحالي `/app/data/server.key`، وملفات WAL/SHM بجوار القاعدة. المستندات المحفوظة في `attachments.content` وصور التسويق في `marketing_assets.content` كـBLOB؛ ليست ملفات رفع متفرقة. ملفات التعليمات والكود في الصورة وفي GitHub.

تحقق من الإنتاج عبر Shell أو واجهة المالك الجديدة `/api/operations/storage` بعد اعتماد التحديث: المسار الحقيقي، وضع WAL، busy timeout، مساحة الملفات، إمكانية الكتابة، ونسب امتلاء النظام. مطابقة المسار مع `/app/data` ليست وحدها إثبات تركيب قرص؛ طابقها أيضًا مع خدمة Render وقرصها. `DB_PATH` و`KEY_PATH` و`BACKUP_DIR` يجب أن تكون داخل المجلد الدائم. لا تستخدم `/app/backups` على Render دون قرص منفصل.

## التشفير والنسخ

1. أنشئ زوج مفاتيح RSA 3072 على جهاز موثوق باستخدام `scripts/generate-recovery-key.mjs`. أدخل `RECOVERY_KEY_PASSPHRASE` سرًا في البيئة، بطول 20 حرفًا فأكثر، لا ضمن سطر الأوامر أو محادثة. السكربت يرفض مجلدًا موجودًا، ويحفظ المفتاح الخاص بصيغة PKCS8 مشفرة. احتفظ بالمفتاح الخاص وكلمة مروره خارج Render وخارج GitHub وخارج النسخة وحدها.
2. ضع المفتاح العام فقط في `BACKUP_PUBLIC_KEY`. إعدادات Render المقترحة: `BACKUP_DIR=/app/data/backups`, `BACKUP_INTERVAL_HOURS=24`, `BACKUP_SOURCE_ROOT=/app`, `BACKUP_REQUIRE_ENCRYPTED=1`, `PERSISTENT_DATA_DIR=/app/data`, `REQUIRE_PERSISTENT_STORAGE=1`.
3. `node scripts/recovery-bundle.mjs` ينشئ لقطة عبر SQLite Online Backup API، يفحص quick_check والعلاقات، ثم يحزم القاعدة والمفتاح والكود وإعدادات التشغيل في `.mebak`. تشفير AES-256-GCM بمفتاح عشوائي لكل نسخة، مغلف بـRSA-OAEP-SHA256. التشفير والضغط والتجزئة تعمل كتدفقات لتقليل استهلاك RAM. لا تُنقل قاعدة حية بمجرد نسخ ملف `.sqlite`، ولا تُرفع ملفات `.key` منفردة.
4. الاستعادة تتحقق من التوثيق المشفر بالكامل قبل فك ضغط الملفات، وتتحقق من المسارات والبصمات وعدد السجلات وسلامة SQLite ومفاتيح التكاملات. ترفض استبدال وجهة موجودة، وتلغي الجلسات في النسخة المستعادة فقط. الإنتاج الأصلي لا يُعدّل.
5. البواقي المؤقتة التي تنشئها العملية نفسها تُزال. النسخ القديمة الموجودة لا تُحذف بهذه الحزمة. السياسة المقترحة للاعتماد: 7 نسخ محلية مشفرة، 30 نسخة يومية خارجية، ونسخة شهرية لمدة 12 شهرًا. لم تُفعّل أي عملية حذف أو دورة احتفاظ سحابية؛ يتطلب ذلك موافقة منفصلة وتحقق مساحة Drive والقرص.

## Google Drive والمهمة المستقلة

التصميم: GitHub Actions مجدول يوميًا 03:17 UTC، ينادي endpoint مخصصًا لتصدير نسخة مشفرة ثم يرفعها إلى مجلد Drive خاص. النسخ الخارجية لا تحتاج جلسة Work. لا يخزن GitHub المفتاح الخاص لفك النسخ.

أنشئ OAuth خاصًا بالنسخ بصلاحية `drive.file`، ومجلدًا خاصًا يتيحه التطبيق. إذا كان OAuth في وضع Testing فقد تنتهي صلاحية refresh token؛ يجب استيفاء إعدادات Google المناسبة للتشغيل المستمر والتحقق عمليًا من تحديث التفويض. لا تستخدم صلاحية الوصول إلى كل Drive لمجرد تجاوز خطأ مجلد.

الأسرار في GitHub Environment باسم `crm-backup`: `CRM_BACKUP_EXPORT_TOKEN`, `DRIVE_CLIENT_ID`, `DRIVE_CLIENT_SECRET`, `DRIVE_REFRESH_TOKEN`, `DRIVE_FOLDER_ID`. يوضع نفس token المخصص، بطول 32 حرفًا عشوائيًا فأكثر، في Render `BACKUP_EXPORT_TOKEN`. هذا المفتاح يتيح تصدير حزمة مشفرة وحالة النسخ وإقرار نجاح التخزين؛ لا يسجّل الدخول إلى CRM ولا يقرأ API العملاء. تفويضه ليس كلمة مرور المالك.

المهمة تتحقق من SHA256 للملف المُنزَّل، وترفض مجلدًا عامًا أو تحميلًا إلى نطاق غير Google، وتتحقق من حجم وبصمة MD5 التي يعيدها Drive ثم تسجل إقرار offsite في CRM. انتهاء Google OAuth، نفاد الحصة، أو عدم وصول التطبيق إلى المجلد يؤدي لفشل واضح، دون ادعاء نجاح أو طباعة الأسرار.

التفعيل يتطلب `CRM_BACKUPS_ENABLED=true` بعد تجربة يدوية ناجحة وتنبيه فشل تجريبي. فعّل رسائل فشل Actions للمالك وتحقق من استلامها؛ رسالة `::error::` وحدها ليست إثبات وصول تنبيه. المهمة لا ترفع نسخة علنية إلى مستودع GitHub أو Artifacts. المتابعة الخارجية كل 15 دقيقة اختيارية عبر `CRM_MONITORING_ENABLED=true`. جدولة GitHub قد تتأخر، وليست ضمان مراقبة فورية.

## اختبار الاستعادة المعزول

```bash
node scripts/restore-bundle.mjs encrypted.mebak /new/empty/recovery
```

مرّر `RECOVERY_PRIVATE_KEY_FILE` و`RECOVERY_KEY_PASSPHRASE` عبر بيئة آمنة. لا تضع القيم في الشرح أو المستودع. الوجهة يجب أن تكون جديدة. ملف `.env.recovery` الناتج يثبت `RECOVERY_MODE=1`، مساري القاعدة والمفتاح، وPUBLIC_ORIGIN محليًا. لا تشغلها بدومين الإنتاج أو Webhooks الإنتاج.

عند تشغيل النسخة المستعادة، حمّل القيم غير السرية اللازمة من `.env.recovery`، وثبّت `RECOVERY_MODE=1` قبل بدء `node app/src/server.mjs`. افحص تسجيل دخول حساب اختبار، العدّ الكلي، بصمات المستندات، ومهام محلية. حلقات الرسائل/التسويق/النسخ والتجارب المباشرة للتكاملات تُمنع من الاتصال بالخارج في وضع الاستعادة. لا تفترض أن قاعدة مستعادة آمنة للإرسال لمجرد فتحها بنجاح.

قبل تحويلها لإنتاج: تحقق من هوية الحسابات، أعد ضبط PUBLIC_ORIGIN وHTTPS، عالج نتائج الإرسال غير المؤكدة قبل أي إعادة، راجع الجلسات والمهام المتأخرة، واعتمد التحويل. لا تفعل الإرسال من النسخة القديمة والجديدة معًا.

## التحديث وRollback

`ci.yml` ينفذ npm ci، الاختبارات، فحص الاعتماديات، وبناء Docker، ويعرض الملفات الحساسة للمراجعة. لا يحتوي أمر نشر أو أسرار إنتاج. ملخص الملفات الحساسة ليس حماية فرع؛ يجب اعتماد GitHub branch protection ومراجعة مالك، واشتراط CI قبل الدمج والنشر. لا تعدل Auto Deploy دون موافقة المالك؛ خيار مناسب هو النشر اليدوي بعد فحوص ناجحة أو الربط بفحوص ناجحة إذا دعم إعداد الحساب ذلك.

`startupPreflight` يفحص قاعدة موجودة للقراءة فقط قبل تشغيل التطبيق. يرفض قاعدة أحدث من إصدار التطبيق ومفتاحًا مفقودًا. عند الحاجة لترحيل قاعدة أقدم، يطلب نسخة مشفرة متسقة قبل الترحيل. لا يوجد ترحيل بيانات PostgreSQL في الحزمة.

الرجوع: سجل commit الناجح وdeploy ID، افحص توافق schema مع الإصدار المستهدف، واحصل على موافقة الانقطاع، ثم استخدم Rollback الرسمي لنسخة بناء محفوظة. الرجوع للكود لا يرجع القرص أو الرسائل المرسلة أو الترحيلات. لا تستعد snapshot القرص مباشرة كبديل لاستعادة SQLite متسقة. عند عدم توافق schema: استعد نسخة مشفرة في خدمة منفصلة، راجع فرق البيانات، ثم اعتمد التحويل. لا تستبدل القرص الحالي تلقائيًا.

## الدومين

المطلوب سجل CNAME جديد واحد فقط: الاسم `crm`، القيمة `mid-east-platform.onrender.com`، TTL افتراضي/300 إن توفر. NS الحالية تتبع Wuilt Orderbox. أضف الدومين المخصص إلى خدمة Render أولًا بعد الموافقة والتحقق من حساب DNS، ثم السجل الجديد، ثم انتظر تحقق الشهادة واختبر HTTPS. لا تعدّل سجل الجذر أو www أو MX/TXT/CAA للموقع والبريد.

لا تغيّر PUBLIC_ORIGIN أو Webhooks أو إعادة توجيه رابط Render حتى اختبار الجلسات والـCSRF وروابط التسجيل على الدومينين. يوفر التحديث ADDITIONAL_ORIGINS لقائمة HTTPS صريحة دون wildcard. بعد تحقق DNS والشهادة وموافقة المالك، يمكن إضافة https://crm.mideastedu-eg.com مع بقاء PUBLIC_ORIGIN على Render أثناء الاختبار؛ وعند التحويل النهائي تُعكس القيم مع إبقاء رابط Render ضمن القائمة للفترة المعتمدة. النطاقات الأجنبية تظل مرفوضة. مجرد نجاح DNS لا يكفي للدخول أو إرسال النماذج. احتفظ برابط Render أثناء الاختبار.

## عند توقف Render أو النقل مستقبلًا

1. على جهاز/سيرفر مستقل، استرجع آخر `.mebak` من Google Drive والمفتاح الخاص من مكانه المنفصل.
2. افحص SHA والتشفير، واستعد إلى مجلد جديد في وضع RECOVERY_MODE. استخدم مجلد `app` للكود و`data` للقاعدة والمفتاح.
3. ابنِ Docker من `app/deploy/Dockerfile`، أو استخدم Node 24 وnpm ci من lockfile. اربط مجلد `data` كقرص دائم. جهّز HTTPS ونسخًا خارجية على المضيف الجديد؛ لا تحتاج Work.
4. راجع تكاملات Meta والتوكنات وWebhooks والفواتير الخارجية؛ لا تغيّر الحسابات أو ترسل تجارب لعملاء حقيقيين.
5. قبل تحويل الإنتاج، أوقف الكتابة على القديم بموافقة المالك، أنشئ نسخة نهائية متسقة، أعد المقارنة والاستعادة، ثم حوّل DNS/Webhooks. معيار RPO اليومي حتى 24 ساعة إذا نجاح النسخ مؤكد، وليس وعدًا بفقد صفر دون مزامنة نهائية. RTO يُقاس بتجربة الاستعادة الفعلية ولا يُخمن.
6. الرجوع يتطلب تحديد السجلات الجديدة التي ظهرت في المضيف البديل، وعدم تشغيل نظامين يرسلان رسائل في الوقت نفسه.

لا تنفذ هذه الخطوات الآن. Render يبقى الاستضافة الإنتاجية.
